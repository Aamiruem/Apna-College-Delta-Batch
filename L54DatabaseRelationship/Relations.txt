SQL One-to-One Relationship (1:1) – Complete Concept
A One-to-One Relationship means:

One row in Table A is connected to only one row in Table B.

And

One row in Table B is connected to only one row in Table A.

Real Life Examples
Table A	Table B	Relationship
Person	Passport	One person has one passport
User	UserProfile	One user has one profile
Employee	ParkingSpace	One employee gets one parking space
Student	StudentIDCard	One student has one ID card
Example Diagram
USERS
+----+--------+
| id | name   |
+----+--------+
| 1  | Aamir  |
| 2  | Ali    |
+----+--------+

USER_PROFILE
+----+---------+---------+
| id | user_id | bio     |
+----+---------+---------+
| 1  |    1    | Coder   |
| 2  |    2    | Designer|
+----+---------+---------+
Here:

User 1 → only one profile

Profile 1 → belongs to only one user

This is One-to-One.

How SQL Creates One-to-One Relationship
We use:

Primary Key

Foreign Key

UNIQUE Constraint

Important Terms
1. Primary Key
Uniquely identifies each row.

id INT PRIMARY KEY
2. Foreign Key
Connects one table to another.

user_id INT,
FOREIGN KEY (user_id) REFERENCES users(id)
3. UNIQUE Constraint
Makes sure one value appears only once.

user_id INT UNIQUE
This is the MOST IMPORTANT part for One-to-One.

Method 1: Separate Primary Key + Unique Foreign Key
Create Parent Table
CREATE TABLE users (
    id INT PRIMARY KEY,
    name VARCHAR(50)
);
Create Child Table
CREATE TABLE user_profile (
    id INT PRIMARY KEY,
    user_id INT UNIQUE,
    bio VARCHAR(100),

    FOREIGN KEY (user_id)
    REFERENCES users(id)
);
Why UNIQUE is Important?
Without UNIQUE, many profiles could use same user_id.

That would become:

❌ One-to-Many

Example:

user_id = 1
user_id = 1
user_id = 1
So we add:

UNIQUE(user_id)
Now only one profile per user is allowed.

Insert Data
Insert Users
INSERT INTO users VALUES
(1, 'Aamir'),
(2, 'Ali');
Insert Profiles
INSERT INTO user_profile VALUES
(1, 1, 'Web Developer'),
(2, 2, 'Designer');
Invalid Insert Example
INSERT INTO user_profile VALUES
(3, 1, 'Another Bio');
❌ ERROR

Because:

user_id = 1
already exists.

UNIQUE constraint prevents duplicate relationship.

Method 2: Shared Primary Key Relationship
This is a stronger One-to-One relationship.

Both tables share same primary key.

Example
Parent Table
CREATE TABLE users (
    id INT PRIMARY KEY,
    name VARCHAR(50)
);
Child Table
CREATE TABLE profiles (
    id INT PRIMARY KEY,

    bio VARCHAR(100),

    FOREIGN KEY (id)
    REFERENCES users(id)
);
How It Works
users.id = profiles.id
Same ID used in both tables.

Example:

users.id = 1
profiles.id = 1
This guarantees exactly one matching row.

Difference Between Both Methods
Method	Description
UNIQUE Foreign Key	Most common
Shared Primary Key	Stronger relationship
Fetch Data Using JOIN
INNER JOIN
SELECT users.name, user_profile.bio
FROM users
INNER JOIN user_profile
ON users.id = user_profile.user_id;
Output
+--------+---------------+
| name   | bio           |
+--------+---------------+
| Aamir  | Web Developer |
| Ali    | Designer      |
+--------+---------------+
DELETE Behavior
Suppose:

DELETE FROM users WHERE id = 1;
What happens to profile?

Depends on:

ON DELETE
ON DELETE CASCADE
Automatically deletes child row.

FOREIGN KEY (user_id)
REFERENCES users(id)
ON DELETE CASCADE
Example
Delete user:

DELETE FROM users WHERE id = 1;
Then profile also deletes automatically.

ON UPDATE CASCADE
If parent ID changes, child updates automatically.

ON UPDATE CASCADE
Full Example with Cascade
CREATE TABLE users (
    id INT PRIMARY KEY,
    name VARCHAR(50)
);

CREATE TABLE profiles (
    id INT PRIMARY KEY,
    user_id INT UNIQUE,
    bio VARCHAR(100),

    FOREIGN KEY (user_id)
    REFERENCES users(id)
    ON DELETE CASCADE
    ON UPDATE CASCADE
);
Advantages of One-to-One Relationship
Advantage	Explanation
Better organization	Separate sensitive data
Security	Store private data separately
Flexibility	Optional information
Faster queries	Smaller tables
When to Use One-to-One
Use when:

✅ Data is optional
✅ Data is sensitive
✅ Large data should be separated
✅ Logical separation needed

Feature	One-to-One	One-to-Many

One-to-One vs Many-to-Many

Common Interview Questions
Q1: How do you create One-to-One relationship?
Using:

Foreign Key

UNIQUE constraint

Q2: Why UNIQUE is required?
To prevent multiple child rows for same parent.

Q3: Difference between One-to-One and One-to-Many?
One-to-One allows only one related row.

One-to-Many allows many related rows.

Best Practice
Most developers use:

FOREIGN KEY + UNIQUE
because it is flexible and easy.

One-to-Few Relationship Using populate() in MongoDB + Mongoose
In MongoDB/Mongoose, a One-to-Few relationship means:

One document → Few related documents
Usually implemented using:

ObjectId

ref

populate()

Real Example
User → Few Phone Numbers
One user can have:

Personal number

Office number

Emergency number

Only a few phone numbers.

How populate() Works
populate() replaces referenced IDs with actual document data.

Step 1: Create Phone Model
phone.js
const mongoose = require("mongoose");

const phoneSchema = new mongoose.Schema({
    number: String
});

const Phone = mongoose.model("Phone", phoneSchema);

module.exports = Phone;
Step 2: Create User Model
user.js
const mongoose = require("mongoose");

const userSchema = new mongoose.Schema({

    name: String,

    phones: [
        {
            type: mongoose.Schema.Types.ObjectId,
            ref: "Phone"
        }
    ]

});

const User = mongoose.model("User", userSchema);

module.exports = User;
Important Part
phones: [
   {
      type: mongoose.Schema.Types.ObjectId,
      ref: "Phone"
   }
]
This means:

One User → Few Phone Documents
Step 3: Insert Data
Create Phone Documents
const Phone = require("./models/phone");

const p1 = await Phone.create({
    number: "9999999999"
});

const p2 = await Phone.create({
    number: "8888888888"
});
Step 4: Create User
const User = require("./models/user");

const user = await User.create({
    name: "Aamir",
    phones: [p1._id, p2._id]
});
Database Storage
User Document
{
   "_id": "u1",
   "name": "Aamir",
   "phones": ["p1", "p2"]
}
Only IDs are stored.

Step 5: Use populate()
const data = await User.findOne({ name: "Aamir" })
    .populate("phones");

console.log(data);
Output
{
   "_id": "u1",
   "name": "Aamir",

   "phones": [
      {
         "_id": "p1",
         "number": "9999999999"
      },
      {
         "_id": "p2",
         "number": "8888888888"
      }
   ]
}
What populate() Did
Before populate:

"phones": ["p1", "p2"]
After populate:

"phones": [
   { full phone document },
   { full phone document }
]
Visual Flow

     |
     | ObjectIds
     ↓

PHONE DOCUMENTS
One-to-Few Structure
One User → Few Phones
This is implemented using:

Array of ObjectIds
Limiting to Few Records
Suppose:

Maximum 3 phone numbers
Before adding:

if(user.phones.length >= 3){

}

Add New Phone
const newPhone = await Phone.create({
    number: "7777777777"
});

user.phones.push(newPhone._id);

await user.save();
Prevent 4th Phone
if(user.phones.length >= 3){
    console.log("Limit reached");
}
Complete Example
User Schema
const userSchema = new mongoose.Schema({

    name: String,

    phones: [
        {
            type: mongoose.Schema.Types.ObjectId,
            ref: "Phone"
        }
    ]
});
Populate Query

    .populate("phones");

One-to-Squillions Relationship (Detailed Explanation)
What is One-to-Squillions?
“One-to-Squillions” is a database design term mostly used in:

MongoDB

NoSQL systems

It means:

One parent document → Massive number of child documents
The child records can become:

Thousands

Millions

Billions

Meaning of “Squillions”
“Squillions” is not a real number.

It informally means:

Very huge amount
Real-World Examples
Parent	Massive Child Records
User	Logs
Post	Comments
Video	Views
Website	Analytics events
IoT Device	Sensor readings
Customer	Transactions
Example
Video → Views
One video can have:

Millions of views
Wrong Design (Embedding)
Suppose you store all views inside video document.

{
   "title": "MongoDB Tutorial",

   "views": [
      {},
      {},
      {},
      ...
      millions of records
   ]
}
Problem
This becomes VERY BAD because:

❌ Huge document size
❌ Slow queries
❌ Memory issues
❌ Update problems
❌ MongoDB document size limit (16MB)

Correct Design
Store child documents separately.

Structure
One Parent → Separate Massive Child Collection
Example Collections
videos Collection
{
   "_id": "v1",
   "title": "MongoDB Tutorial"
}
views Collection
{
   "_id": "view1",
   "video_id": "v1",
   "user": "Aamir",
   "time": "2026-05-08"
}
Relationship
One Video → Millions of Views
Why Separate Collection?
Because child records grow infinitely.

One-to-Squillions in MongoDB
MongoDB best practice:

✅ Parent document stays small
✅ Child documents stored separately
✅ Use references

Mongoose Implementation
Step 1: Create Parent Model
video.js
const mongoose = require("mongoose");

const videoSchema = new mongoose.Schema({
    title: String
});

module.exports = mongoose.model("Video", videoSchema);
Step 2: Create Child Model
view.js
const mongoose = require("mongoose");

const viewSchema = new mongoose.Schema({

    video: {
        type: mongoose.Schema.Types.ObjectId,
        ref: "Video"
    },

    user: String,

    viewedAt: {
        type: Date,
        default: Date.now
    }

});

module.exports = mongoose.model("View", viewSchema);
Important Design
Notice:

video: {
   type: mongoose.Schema.Types.ObjectId,
   ref: "Video"
}
This creates:

Many child documents referencing one parent
Insert Example
Create Video
const video = await Video.create({
    title: "MongoDB Tutorial"
});
Add Millions of Views
await View.create({
    video: video._id,
    user: "Aamir"
});
Each view becomes separate document.

Why This Is Best?
Because:

Views can grow infinitely
without affecting parent document size.

Query Example
Find Views of Video
const views = await View.find({
    video: videoId
});
Count Total Views
const total = await View.countDocuments({
    video: videoId
});

Difference from One-to-Few
Feature	One-to-Few	One-to-Squillions
Child count	Small	Massive
Storage	Array possible	Separate collection
Embedding	Good	Bad

Embedding vs Referencing
One-to-Few
Embedding often works:

{
   "phones": [
      "9999999999",
      "8888888888"
   ]
}
One-to-Squillions
Embedding becomes dangerous:

{
   "comments": [
      millions...
   ]
}
❌ Very bad design.

Best Practice
For One-to-Squillions:

✅ Use separate collection
✅ Use references
✅ Add indexes
✅ Use pagination
✅ Use aggregation

Indexing Important
Because millions of records exist.

Add index:

viewSchema.index({ video: 1 });
Makes queries fast.

Pagination Example
Never load millions at once.

Use:

const comments = await Comment.find({
    post: postId
})
.limit(20)
.skip(40);
